# Правила агентної розробки

Ці правила діють для AI-агентів і людей. Вони важливіші за швидкість виконання задачі.

## 1. Перед початком

1. Прочитай запит, пов'язану спеку, план та інструкції репозиторію.
2. Перевір робочу директорію і `git status`.
3. Не видаляй і не перезаписуй чужі незавершені зміни.
4. Знайди чинні патерни в коді. Не створюй другий спосіб робити те саме без причини.
5. Якщо вимога змінює поведінку, API, дані або інфраструктуру — спочатку потрібна погоджена спека.

## 2. Джерела правди

Для вимог використовуйте такий пріоритет:

1. остання погоджена версія спеки;
2. зафіксовані рішення в спеці;
3. план реалізації;
4. опис задачі та повідомлення в обговоренні.

Якщо джерела суперечать одне одному — зупинись і попроси рішення. Не обирай мовчки.

Код показує поточну реалізацію, але не може самостійно змінити погоджені вимоги.

## 3. План перед кодом

- Один пункт плану має давати один перевірюваний результат.
- Укажи конкретні файли, команди й очікуваний результат перевірки.
- Спочатку зміни контракти й тести, потім реалізацію.
- Не додавай «заодно» рефакторинг, нові залежності чи функції поза спекою.
- Якщо план перестав відповідати реальності — онови план і зафіксуй причину до продовження роботи.

## 4. Під час реалізації

- Роби найменшу зміну, яка виконує критерії приймання.
- Тримай бізнес-логіку окремо від HTTP, ORM, черг та зовнішніх SDK.
- Контролери лише приймають запит, викликають use case і формують відповідь.
- Зовнішні сервіси підключай через адаптери та чіткі інтерфейси.
- Не дублюй знання: одна схема конфігурації, один контракт API, один спосіб логування.
- Нову залежність додавай лише з поясненням, навіщо вона потрібна і чому стандартних засобів недостатньо.
- Не змінюй публічний контракт без версіонування або плану сумісності.

## 5. Тести й докази

Агент не має права писати «готово», поки не виконав релевантні перевірки.

Мінімум:

1. форматування та lint;
2. typecheck;
3. тести зміненого модуля;
4. інтеграційні або e2e-тести для меж системи;
5. ручна перевірка критичного сценарію, якщо автоматичного тесту недостатньо.

У звіті вкажи точні команди та їх результат. Не приховуй пропущені або невдалі перевірки.

Тестуйте поведінку, а не внутрішню реалізацію. Для кожного виправлення дефекту спочатку відтворіть проблему тестом, якщо це практично можливо.

## 6. Дані та міграції

- Міграції мають бути повторюваними, перевіреними на порожній і наявній базі.
- Для production-змін використовуйте backward-compatible послідовність: **expand → migrate → contract**.
- Не видаляйте колонку або контракт в одному релізі з припиненням його використання.
- Опишіть rollback або прямо поясніть, чому він неможливий і як відновлюватися.
- Seed-дані не повинні містити персональні або production-дані.

## 7. Безпека

- Ніколи не додавайте секрети, токени, паролі або production-дані в git, логи, тести чи приклади.
- Усі зовнішні дані валідуються на вході.
- Авторизація перевіряється на сервері для кожної захищеної операції.
- Логи не повинні містити JWT, cookies, OTP, платіжні реквізити або персональні дані.
- Для auth, платежів, ролей і доступу додайте негативні тести.
- Нові endpoints мають мати обмеження розміру запиту, timeout і rate limit там, де це потрібно.

## 8. Спостережуваність і помилки

- Використовуйте структуровані логи з `requestId` або `correlationId`.
- Помилка повинна мати зрозумілий код для клієнта і достатній контекст у внутрішньому логу.
- Не повертайте stack trace чи внутрішні деталі клієнту.
- Для фонового job визначте retry, backoff, idempotency та поведінку після остаточної помилки.
- Для критичної зміни опишіть метрики, алерти й ознаки успішного rollout.

## 9. Робота кількох агентів

- Детальний протокол: [Взаємодія агентів](./AGENT_COLLABORATION.md).
- Один агент або інтегратор відповідає за кінцевий результат.
- Паралельно виконуйте лише незалежні частини роботи.
- Перед делегуванням визначте власника файлів і очікуваний результат.
- Два агенти не повинні одночасно редагувати один файл.
- Агент не комітить і не скасовує зміни іншого агента.
- Інтегратор перечитує diff, запускає спільні перевірки та вирішує конфлікти.
- Кожна передача роботи оформлюється через [handoff](./templates/HANDOFF_TEMPLATE.md), а не лише повідомленням «готово».

## 10. Git і звітність

- Один commit — одна логічна зміна.
- Використовуйте Conventional Commits: `feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`.
- Не використовуйте destructive git-команди без прямого дозволу.
- Не робіть commit або push, якщо користувач чи workflow цього не просить.
- Фінальний звіт має містити: що змінено, де змінено, що перевірено, що залишилося ризиком.

## 11. Заборонено

- Починати нетривіальну реалізацію без погоджених критеріїв приймання.
- Вигадувати вимоги або мовчки змінювати scope.
- Маскувати помилки порожнім `catch` або вимиканням перевірок.
- Додавати `any`, `eslint-disable`, пропуск тесту чи небезпечний cast без пояснення.
- Заявляти про успішну перевірку, якої не було.
- Залишати `TODO` замість необхідної для задачі реалізації.
- Змінювати lockfile без фактичної зміни залежностей.

## Коротке правило

> Не здогадуйся, не розширюй scope, не приховуй помилки. Спочатку домовся, потім зміни, потім доведи результат.
