# Взаємодія агентів

Цей документ описує, як агенти ділять роботу, повідомляють про прогрес, передають результат і доробляють роботу одне одного.

Головне правило:

> Передавати потрібно не розмову, а перевірюваний стан роботи: мету, межі, зміни, рішення, докази та наступну дію.

## 1. Ролі

| Роль            | Відповідальність                                                                         |
| --------------- | ---------------------------------------------------------------------------------------- |
| **Координатор** | Розбиває задачу, визначає залежності, призначає власників і стежить за спекою та планом. |
| **Виконавець**  | Реалізує один чітко обмежений результат і надає докази перевірки.                        |
| **Рев'юер**     | Незалежно перевіряє відповідність спеці, коректність diff, тести, ризики й документацію. |
| **Інтегратор**  | Об'єднує частини, вирішує конфлікти та запускає спільні перевірки.                       |
| **Спеціаліст**  | Досліджує вузьке питання: безпеку, базу даних, API, продуктивність або інфраструктуру.   |

Один агент може мати кілька ролей, але для ризикових змін автор не повинен бути єдиним рев'юером.

## 2. Стани задачі

```text
Unclaimed → Claimed → In Progress → Ready for Review → Done
                              ↘ Blocked       ↙ Changes Requested
```

- **Unclaimed** — власника немає.
- **Claimed** — власник, scope і файли зафіксовані.
- **In Progress** — робота виконується.
- **Ready for Review** — виконавець завершив свою частину й надав докази.
- **Changes Requested** — рев'юер повернув конкретні зауваження.
- **Blocked** — продовження потребує рішення, доступу або зовнішньої зміни.
- **Done** — результат прийнятий інтегратором і пройшов фінальні перевірки.

Тільки інтегратор або координатор переводить спільну задачу в `Done`.

## 3. Коли агент робить сам, а коли передає

### Доробити самостійно

Агент продовжує сам, якщо:

- наступний крок прямо випливає з погодженого плану;
- зміна локальна й не потребує іншої спеціалізації;
- контекст уже завантажений, а передача коштуватиме дорожче за виконання;
- агент володіє потрібними файлами й не конфліктує з іншою роботою;
- можна безпечно перевірити результат.

### Делегувати

Роботу варто передати, якщо:

- підзадача незалежна й може виконуватися паралельно;
- потрібна окрема експертиза або незалежне рев'ю;
- підзадача має власний перевірюваний результат;
- вона не вимагає одночасного редагування тих самих файлів;
- координатор може чітко описати вхід, вихід і критерії приймання.

### Не делегувати

Не передавайте:

- нечіткий запит «подивись і виправ»;
- рішення, яке ще не погоджене в спеці;
- маленький крок, для якого пояснення довше за виконання;
- роботу над файлом, який у цей момент редагує інший агент;
- відповідальність за фінальну інтеграцію без явного призначення інтегратора.

## 4. Контракт перед початком підзадачі

Перед делегуванням координатор передає:

1. **Мету** — один очікуваний результат.
2. **Контекст** — посилання на спеку, план і залежні рішення.
3. **Scope** — що входить і що не входить.
4. **Власність** — точні файли або модулі, які можна змінювати.
5. **Вхідні дані** — контракти, типи, fixtures або API.
6. **Критерії приймання** — як зрозуміти, що підзадача виконана.
7. **Перевірки** — точні команди або ручний сценарій.
8. **Формат повернення** — код, дослідження, review findings або handoff.

Приклад хорошого доручення:

```text
Мета: реалізувати RedisIndicator для SPEC-2026-001.
Scope: лише libs/health/redis.indicator.ts і його unit-тест.
Не змінювати: controller, Compose, PrismaIndicator.
Контракт: check(): Promise<'up' | 'down'>, timeout 1000 ms.
Приймання: тести success, error і timeout проходять.
Перевірка: pnpm test -- redis.indicator.spec.ts.
Повернути: diff, виконані команди, рішення й залишкові ризики.
```

## 5. Як агенти спілкуються

Повідомлення має бути коротким, але достатнім для дії.

### Обов'язкові правила

- Відокремлюйте **факт**, **припущення** і **пропозицію**.
- Називайте конкретний файл, критерій, команду або помилку.
- Повідомляйте про зміну scope до реалізації, а не після.
- Не пересилайте весь внутрішній хід думок; передавайте рішення й докази.
- Оновлюйте статус після значущого результату, блокера або зміни плану.
- Не пишіть «готово» без переліку перевірок.
- Якщо відповідь потрібна для продовження — поставте одне конкретне питання.

### Короткий статус

```text
Статус: In Progress
Завершено: Redis indicator і unit-тести.
Зараз: інтеграція з HealthService.
Ризик: timeout ще не перевірений e2e.
Наступне оновлення: після pnpm test:e2e -- health.
```

### Блокер

```text
Статус: Blocked
Блокер: спека не визначає, чи недоступність MinIO має робити API not ready.
Перевірено: SPEC-2026-001, README і чинний health module — рішення немає.
Варіанти: A) не перевіряти MinIO; B) повертати 503.
Рекомендація: A, бо завантаження файлів не потрібне для всіх API-сценаріїв.
Потрібне рішення: підтвердити A або B.
```

## 6. Власність і паралельна робота

- Кожна активна підзадача має одного власника.
- До початку агент оголошує файли, які планує змінювати.
- Спільний контракт спочатку погоджується, потім залежні агенти працюють паралельно.
- Якщо двом агентам потрібен один файл, його змінює один власник або робота виконується послідовно.
- Підзадачі інтегруються по одній; після кожної запускаються релевантні перевірки.
- Останнім запускається спільний набір перевірок у чистому інтегрованому стані.

Паралельна робота корисна для незалежних частин, наприклад:

```text
Agent A: PostgreSQL indicator + unit tests
Agent B: Redis indicator + unit tests
Agent C: OpenAPI і README
Integrator: HealthService, controller, Compose та e2e
```

## 7. Види передачі роботи

### Завершена частина

Передавайте як `Ready for Review`, якщо:

- scope виконано повністю;
- diff перечитано;
- локальні перевірки виконано;
- відхилення й ризики записані;
- немає прихованих наступних кроків.

### Незавершена частина

Передавайте як `Partial` або `Blocked`, а не `Done`. Обов'язково вкажіть:

- що вже працює;
- що ще не працює;
- який стан файлів безпечний;
- які перевірки проходять або падають;
- з якого точного кроку продовжувати;
- чого не можна робити без рішення.

Незавершену роботу не можна маскувати формулюванням «майже готово».

## 8. Формат handoff

Використовуйте [шаблон handoff](./templates/HANDOFF_TEMPLATE.md).

Мінімальний формат:

```text
Статус: Ready for Review | Partial | Blocked
Мета: <який результат передається>
Scope: <що входило і не входило>
Змінено: <файли й поведінка>
Рішення: <важливі рішення та причини>
Перевірено: <команда → PASS/FAIL>
Не завершено: <явний список>
Ризики: <залишкові ризики>
Наступна дія: <одна конкретна дія наступного агента>
```

## 9. Як приймати чужу роботу

Наступний агент не продовжує навмання і не довіряє слову `PASS` без перевірки.

1. Прочитати спеку, відповідний пункт плану й handoff.
2. Перевірити `git status` і diff у заявлених файлах.
3. Переконатися, що зміни не виходять за scope.
4. Запустити передані перевірки повторно.
5. Перевірити негативні сценарії та інтеграційні межі.
6. Зафіксувати один результат:
   - `Accepted` — можна інтегрувати;
   - `Changes Requested` — є конкретні виправлення;
   - `Blocked` — потрібне рішення або доступ.
7. Оновити план і власність задачі перед продовженням.

## 10. Як доробляти чужу роботу

- Продовжуйте з переданого safe point, а не переписуйте все автоматично.
- Зберігайте чинні рішення, якщо вони відповідають спеці.
- Якщо потрібна зміна контракту або архітектури — поверніться до погодження.
- Не скасовуйте чужий diff лише тому, що віддаєте перевагу іншому стилю.
- Виправляйте причину failing test, а не вимикайте тест.
- Після доробки надайте новий handoff, який охоплює і прийняту, і додану роботу.

## 11. Review findings

Зауваження мають бути конкретними й пріоритезованими:

| Рівень | Значення                                                       |
| ------ | -------------------------------------------------------------- |
| `P0`   | Втрата даних, критична вразливість або повна непрацездатність  |
| `P1`   | Порушення основного сценарію або контракту                     |
| `P2`   | Реальна помилка в граничному сценарії, надійності чи підтримці |
| `P3`   | Невелике покращення, яке не блокує приймання                   |

Приклад:

```text
[P1] Worker може повторно списати кошти після retry
Файл: src/payments/capture-payment.handler.ts
Умова: provider повернув timeout після успішного списання.
Наслідок: повторний job викликає capture без idempotency key.
Потрібно: передавати стабільний key і додати regression test.
```

## 12. Завершення спільної роботи

Інтегратор перед `Done`:

1. перевіряє відповідність усім критеріям спеки;
2. перечитує інтегрований diff;
3. запускає повний релевантний набір перевірок;
4. перевіряє міграції, конфігурацію й документацію;
5. записує невиконані перевірки та залишкові ризики;
6. оновлює план, changelog і README;
7. передає фінальний звіт координатору або користувачу.

## 13. Антипатерни

- «Я зробив свою частину» без файлів, перевірок і наступної дії.
- Передача сирого чату замість структурованого handoff.
- Одночасне редагування спільного файлу кількома агентами.
- Делегування задачі без scope і критеріїв приймання.
- Приймання роботи лише за повідомленням автора.
- Приховане переписування чужої реалізації.
- Статус `Done`, коли integration/e2e не запускалися.
- Нескінченні статуси без нового результату, блокера або рішення.
