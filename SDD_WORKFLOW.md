# SDD workflow

SDD — це **Spec-Driven Development**: розробка, у якій перевірюваний опис поведінки передує коду.

## Стани документа

| Статус        | Значення                                               |
| ------------- | ------------------------------------------------------ |
| `Draft`       | Документ обговорюється, реалізацію починати не можна   |
| `Approved`    | Вимоги погоджено, можна створювати або виконувати план |
| `In Progress` | Реалізація триває                                      |
| `Done`        | Критерії виконано і перевірено                         |
| `Superseded`  | Документ замінено новішим рішенням                     |

Змінювати погоджену поведінку без нової ревізії спеки заборонено.

## Крок 1. Сформулювати запит

Запит має відповісти на три питання:

- Яка проблема існує?
- Для кого вона важлива?
- Який результат вважатиметься корисним?

Погано: «Зробити healthcheck».

Добре: «Оркестратор повинен відрізняти живий процес від API, готового приймати трафік після підключення PostgreSQL і Redis».

## Крок 2. Створити спеку

Використовуйте [шаблон спеки](./templates/SPEC_TEMPLATE.md).

Спека описує **що**, а не покроково **як**. Вона повинна містити:

- контекст і проблему;
- цілі та явні не-цілі;
- сценарії й контракти;
- критерії приймання;
- нефункціональні вимоги;
- помилки й граничні випадки;
- rollout, rollback та спостережуваність для ризикових змін;
- відкриті питання та прийняті рішення.

Кожен критерій приймання має бути однозначно перевірюваним.

Погано: «Endpoint працює швидко».

Добре: «За справних залежностей `GET /api/v1/health/ready` повертає `200` не довше ніж за 500 мс у локальному Compose-середовищі».

## Крок 3. Погодити спеку

Перед статусом `Approved` перевірте:

- scope має чіткі межі;
- немає суперечностей;
- усі терміни зрозумілі;
- API та дані описані;
- критерії можна перевірити;
- ризики мають план контролю.

Погодження фіксується в секції `Approval` документа або в системі керування задачами з посиланням на спеку.

## Крок 4. Створити план

Використовуйте [шаблон плану](./templates/PLAN_TEMPLATE.md).

План описує точний шлях від поточного стану до погодженої поведінки:

- конкретні файли;
- порядок змін;
- тести до або разом із реалізацією;
- команди перевірки;
- міграцію, rollout і rollback;
- залежності між кроками.

Кожен крок повинен бути малим, самодостатнім і перевірюваним.

## Крок 5. Реалізувати

Для кожного пункту плану:

1. Зафіксуйте очікувану поведінку тестом або контрактом.
2. Переконайтеся, що перевірка відтворює відсутню поведінку чи дефект.
3. Зробіть мінімальну реалізацію.
4. Запустіть локальні перевірки.
5. Позначте пункт виконаним і запишіть відхилення від плану.

Якщо з'явилася нова вимога — поверніться до спеки. Не ховайте новий scope усередині реалізації.

## Крок 6. Перевірити

Зіставте результат не лише з планом, а насамперед зі спекою.

Для кожного критерію приймання вкажіть доказ:

| Критерій | Доказ                                                 |
| -------- | ----------------------------------------------------- |
| READY-1  | e2e-тест `health.e2e-spec.ts`                         |
| READY-2  | команда `docker compose stop redis` і відповідь `503` |

Виконайте [контрольний список якості](./QUALITY_CHECKLIST.md).

## Крок 7. Оновити документацію

- Додайте changelog для помітної зміни поведінки, API, конфігурації або операцій.
- Оновіть README, якщо користувачеві чи розробнику тепер треба діяти інакше.
- Оновіть OpenAPI, `.env.example`, runbook або діаграми, якщо вони стали неактуальними.
- Переведіть спеку й план у `Done` та додайте посилання на реалізацію.

## Як змінювати погоджену спеку

1. Не переписуйте історію без пояснення.
2. Збільште ревізію документа.
3. Додайте запис у `Revision history`.
4. Позначте змінені критерії.
5. Повторно погодьте зміни.
6. Оновіть план, тести й changelog.

## Коли повна спека не потрібна

Для очевидної друкарської помилки або форматування достатньо короткого опису зміни й перевірки diff. Якщо зміна може вплинути на поведінку — це вже не дрібна зміна.
