# Readiness-перевірка PostgreSQL і Redis

## Summary

Додати endpoint `GET /api/v1/health/ready`, який дозволяє Docker Compose та платформі розгортання відрізнити запущений процес API від процесу, готового обробляти запити після підключення PostgreSQL і Redis.

## Контекст і проблема

Звичайна перевірка `live` підтверджує лише роботу Node.js-процесу. Якщо PostgreSQL або Redis недоступні, процес залишається живим, але не може коректно обробляти основні сценарії. Оркестратор не повинен направляти на нього трафік.

## Цілі

- Надати окремі liveness і readiness endpoints.
- Повертати стабільний машинозчитуваний результат для PostgreSQL і Redis.
- Не розкривати credentials, URL підключення або stack traces.

## Не-цілі

- Перевірка MinIO та зовнішніх SMS/payment providers.
- Автоматичне відновлення PostgreSQL або Redis.
- Побудова повного monitoring dashboard.

## Користувачі та сценарії

### Сценарій 1: Усі залежності доступні

**Передумови:** API підключається до PostgreSQL і Redis.

**Дія:** Оркестратор викликає `GET /api/v1/health/ready`.

**Результат:** API повертає `200`, загальний статус `ok` і статус `up` для обох залежностей.

### Сценарій 2: Redis недоступний

**Передумови:** API працює, PostgreSQL доступний, Redis недоступний.

**Дія:** Оркестратор викликає readiness endpoint.

**Результат:** API повертає `503`, статус `error`, PostgreSQL — `up`, Redis — `down`.

## Функціональні вимоги

| ID   | Вимога                                                                                    |
| ---- | ----------------------------------------------------------------------------------------- |
| FR-1 | `GET /api/v1/health/live` повертає `200`, якщо Node.js-процес може обробляти HTTP-запити. |
| FR-2 | `GET /api/v1/health/ready` перевіряє PostgreSQL командою `SELECT 1`.                      |
| FR-3 | Readiness перевіряє Redis командою `PING`.                                                |
| FR-4 | Якщо хоча б одна залежність недоступна або перевищила timeout, endpoint повертає `503`.   |
| FR-5 | Endpoint не потребує автентифікації.                                                      |

## Контракти

### Liveness

```http
GET /api/v1/health/live
```

```json
{
  "status": "ok"
}
```

### Readiness: успіх

```http
GET /api/v1/health/ready
```

```json
{
  "status": "ok",
  "checks": {
    "postgres": "up",
    "redis": "up"
  }
}
```

### Readiness: помилка залежності

```json
{
  "status": "error",
  "checks": {
    "postgres": "up",
    "redis": "down"
  },
  "requestId": "9a284ae0-2617-4da3-8153-1a8cff576845"
}
```

## Дані

Схема PostgreSQL не змінюється. Endpoint не читає бізнес-дані й не створює записи.

## Події та jobs

Нові події та фонові jobs не створюються.

## Помилки та граничні випадки

| Умова                            | Очікувана поведінка                                                      |
| -------------------------------- | ------------------------------------------------------------------------ |
| PostgreSQL недоступний           | `503`, `postgres: down`                                                  |
| Redis недоступний                | `503`, `redis: down`                                                     |
| Обидві залежності недоступні     | `503`, обидва статуси `down`                                             |
| Перевірка триває понад 1 секунду | Вона завершується як `down`                                              |
| Внутрішня неочікувана помилка    | `503`, без stack trace у відповіді; повна помилка в структурованому логу |

## Нефункціональні вимоги

- **Продуктивність:** за справних локальних залежностей відповідь не довше 500 мс.
- **Timeout:** не більше 1 секунди на одну залежність.
- **Навантаження:** перевірка не створює нове підключення для кожного запиту.
- **Безпека:** відповідь не містить host, port, credentials, SQL або stack trace.
- **Спостережуваність:** помилка логується з `requestId`, назвою залежності й без секретів.
- **Сумісність:** чинний `live` endpoint не змінює контракт.

## Критерії приймання

- [ ] **AC-1:** За доступних PostgreSQL і Redis readiness повертає `200` та обидва статуси `up`.
- [ ] **AC-2:** За недоступного Redis readiness повертає `503`, `redis: down` і `postgres: up`.
- [ ] **AC-3:** За недоступного PostgreSQL readiness повертає `503`, `postgres: down` і `redis: up`.
- [ ] **AC-4:** Жодна error response не містить секретів або stack trace.
- [ ] **AC-5:** Docker Compose healthcheck використовує readiness endpoint.
- [ ] **AC-6:** OpenAPI та README описують обидва endpoints.

## Rollout і rollback

1. Розгорнути новий endpoint без зміни healthcheck.
2. Викликати endpoint вручну й перевірити логи.
3. Перевести healthcheck на `/api/v1/health/ready`.
4. Спостерігати за restart count і latency протягом 30 хвилин.

Rollback: повернути healthcheck на `/api/v1/health/live`, після чого відкотити застосунок. Дані не змінюються.

## Ризики

| Ризик                                          | Імовірність/вплив | Контроль                                                    |
| ---------------------------------------------- | ----------------- | ----------------------------------------------------------- |
| Короткий збій Redis прибере API з балансування | Medium/Medium     | Timeout 1 с, без автоматичного restart за readiness failure |
| Healthcheck створить зайве навантаження        | Low/Low           | Використання наявних connection pools, interval 10 с        |
